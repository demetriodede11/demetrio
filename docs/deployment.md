# Docker и деплой на VPS

[К основной документации](../README.md)

## Общая схема

Один workflow **«Проверки, сборка и деплой»** в `pipeline.yml` запускается при push
в любую ветку или вручную. Проверки выполняются для всех веток, сборка образа
и деплой — только для `main`. Каждая джоба получает отдельную временную ВМ GitHub:

```text
Пуш в любую ветку / Run workflow
  │
  ▼
build — Проверки и сборка образа, ВМ GitHub №1
  Checkout коммита → npm ci → next typegen
  Параллельно: ESLint + Prettier + TypeScript
  Другие ветки: завершение после проверок
  main, все проверки успешны → Docker: npm ci → next build
  Готовый образ → image.tar.gz → artifact GitHub
  │ только после успешного build
  ▼
deploy — Деплой на VPS, ВМ GitHub №2
  Ожидание завершения другого Deploy
  Checkout текущего main → проверка актуальности релиза
  Подготовка SSH → скачивание artifact → передача четырёх файлов
  │
  ▼
VPS — run-deploy.sh → deploy.sh
  Загрузка образа → замена контейнера → проверка здоровья
  ├── успех: приложение обновлено, временные файлы удалены
  └── ошибка при замене: попытка восстановить предыдущий контейнер
```

Любая ошибка ESLint, Prettier или TypeScript блокирует сборку образа и деплой.
Джобы не имеют общей файловой системы: образ передаётся через artifact,
его идентификатор — через `needs.build.outputs.release_id`.
На VPS устанавливать пакеты или собирать приложение не нужно.

### Новый push и очередь

- Новый push отменяет предыдущий `build` той же ветки и запускает новый.
- Начатый `deploy` не отменяется новым push. Новый `build` выполняется независимо.
- Готовые Deploy ждут друг друга в отдельной группе `concurrency`.
- После ожидания `check-release.sh` сравнивает SHA образа с текущим `main`.
  Устаревший автоматический релиз пропускает SSH, скачивание и обновление VPS.
- **Re-run — явное ручное действие:** повторный запуск допускает старый коммит.
  Это позволяет повторить неудачный деплой или вернуть выбранную прежнюю версию.

Общей отмены всего workflow нет. `queue: max` допускает до 100 ожидающих Deploy;
при переполнении GitHub отменяет новые ожидающие джобы. Дополнительная блокировка
`flock` на VPS защищает от одновременной замены контейнера ручным скриптом.

Если новый push появился уже после проверки актуальности, начатый деплой завершается,
а новый релиз идёт следом. Ошибка новой сборки оставляет последнюю работающую версию.
Кейсы с push, очередью, повторами и откатами — в [отдельной инструкции](deployment-cases.md).

В схемах `WORKSPACE` — корень checkout, `RUNNER_TEMP` — временная папка ВМ GitHub.
`<release_id>` имеет формат `<SHA коммита>-<ID запуска workflow>-<номер попытки сборки>`.

## Где находятся настройки и скрипты

```text
Репозиторий/
├── .github/workflows/pipeline.yml      ← две джобы и правила их запуска
└── deploy/
    ├── Dockerfile                   ← сборка образа приложения
    ├── Dockerfile.dockerignore      ← исключения из контекста сборки
    ├── deploy.sh                    ← замена контейнера и восстановление на VPS
    ├── run-deploy.sh                ← запуск независимо от SSH, логи и результат
    └── ci/                          ← выполняются на ВМ GitHub
        ├── build-image.sh           ← сборка и упаковка образа
        ├── check-release.sh         ← проверка идентификатора и актуальности
        ├── prepare-deploy.sh        ← проверка SSH и запуск SSH-агента
        ├── prepare-config.mjs       ← проверка переменных, создание файлов
        ├── upload-release.sh       ← передача выпуска и запуск run-deploy.sh
        └── cleanup.sh              ← удаление временных файлов GitHub
```

Скрипты `ci/` запускаются из корня репозитория. Контекст Docker-сборки — тоже
корень проекта. `Dockerfile.dockerignore` исключает локальные настройки и секреты.
Отдельных workflow и собственных обращений к GitHub API для связи этапов нет;
достаточно разрешения `contents: read`.

## Ветки и окружения

| Ветка                                           | Что выполняется                                                                                            |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `main`                                          | Установка зависимостей → генерация типов маршрутов → ESLint, Prettier, TypeScript → сборка образа → деплой |
| Любая другая, включая `feature/*` и `release/*` | Установка зависимостей → генерация типов маршрутов → ESLint, Prettier, TypeScript                          |

На остальных ветках джоба называется **«Проверки»**: шаги сборки и сохранения образа
пропускаются, джоба Deploy не запускается. `next typegen` генерирует типы маршрутов,
но не выполняет production-сборку приложения. Push тега не запускает workflow.
Ручной запуск на выбранной ветке соблюдает те же условия.

Группа отмены `build` включает ветку: новый push отменяет только предыдущие проверки
или сборку той же ветки. Работа в других ветках не прерывает `main` и его Deploy.

Отдельный workflow для каждой ветки не требуется. Для добавления окружения понадобятся
свои Secrets, целевые контейнеры и группа очереди деплоя. Отдельные workflow полезны
для самостоятельных процессов: например, ручного отката или ночных проверок.

## Подготовка

На VPS нужны Docker, Bash, `flock`, `setsid`, `nohup`, GNU `tail`, свободный порт 80
и вход по SSH на порту 22. Эти утилиты доступны в используемой Ubuntu.
Docker Compose не требуется. Публичный ключ должен разрешать вход пользователю деплоя.

В GitHub откройте **Settings → Secrets and variables → Actions → Repository secrets**.
Добавьте `HOST_IP`, `USERNAME`, `SSH_PRIVATE_KEY`, `SSH_HOST_FINGERPRINT`,
`API_BASE_URL` и `APP_ORIGIN`. Форматы и необязательные настройки —
в [справочнике переменных окружения](environment.md).

Отпечаток получите в доверенной консоли VPS:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Откройте входящий TCP-порт 80 в настройках VPS и firewall, если он включён.
HTTP по IP — временный режим: для авторизации с Secure-cookie нужен HTTPS.

## 1. Проверки — ВМ GitHub №1, джоба build

Checkout получает коммит запуска. Затем настраивается Node.js 24, `npm ci`
устанавливает зависимости, а `next typegen` создаёт типы маршрутов.
После этого параллельно выполняются ESLint, Prettier и `tsc --noEmit`.

```text
ВМ build
└── WORKSPACE/
    ├── src/, public/, deploy/, ...  ← исходники из Git
    ├── package.json, package-lock.json
    ├── node_modules/               ← добавил npm ci
    └── .next/types/                ← добавил next typegen
```

Кеш npm хранит скачанные пакеты; `npm ci` всё равно устанавливает зависимости.
Эти `node_modules` нужны проверкам на ВМ, в Docker они не копируются.

## 2. Сборка образа — та же ВМ GitHub №1

### Внутри Docker

После успешных проверок `build-image.sh` собирает `demetrio:<release_id>` для
`linux/amd64`. Исходники и Dockerfile берутся из того же проверенного коммита.
Dockerfile содержит три стадии; `/app` находится внутри Docker:

```text
Стадия dependencies             Стадия builder
/app/                           /app/
├── package.json                ├── package.json, package-lock.json, .npmrc
├── package-lock.json           ├── node_modules/       ← из dependencies
├── .npmrc                      ├── src/, public/, ...  ← из контекста сборки
└── node_modules/ ← npm ci      └── .next/               ← результат next build
                                    ├── standalone/
                                    ├── static/
                                    └── ...
```

Финальная стадия получает только файлы для запуска:

```text
Готовый образ demetrio:<release_id>
└── /app/
    ├── server.js          ← сервер Next из standalone
    ├── package.json
    ├── node_modules/      ← зависимости, отобранные Next для запуска
    ├── public/
    └── .next/
        ├── server/
        ├── static/
        └── ...
```

Образ запускается от пользователя `nextjs`, слушает порт 3000 и имеет `HEALTHCHECK`.
SSH-ключ и переменные приложения в образ не добавляются. Установка пакетов внутри
Docker отдельная от установки для проверок: её результат нужен внутри образа.

### На ВМ после сборки

`docker image save` выгружает образ, `gzip` сжимает его:

```text
ВМ build
├── WORKSPACE/
│   ├── src/, public/, deploy/, ...
│   ├── node_modules/                 ← остались от проверок
│   └── .next/types/                  ← остались от next typegen
├── RUNNER_TEMP/demetrio-image/
│   └── image.tar.gz                  ← архив готового образа
└── Внутреннее хранилище Docker
    └── demetrio:<release_id>
```

Docker-сборка не записывает свою `.next` или зависимости в `WORKSPACE`.
`build-image.sh` пишет `release_id` в `GITHUB_OUTPUT`; шаг `image` передаёт его
в output джобы `build`. Он используется и в имени artifact, и в следующей джобе.

```text
ВМ build                    Хранилище GitHub                 ВМ deploy
image.tar.gz ── загрузка ──► demetrio-<release_id> ──────────► image.tar.gz
                            хранится 7 дней
```

После завершения джобы её ВМ удаляется. Архив остаётся в GitHub.

## 3. Подготовка деплоя — ВМ GitHub №2, джоба deploy

### Проверка релиза

Джоба допускается только для `main` после успешного `build`. Получив очередь, она делает
checkout текущего `main`: оттуда берутся поддерживаемые скрипты деплоя.
`check-release.sh` проверяет соответствие идентификатора коммиту и запуску workflow,
затем сравнивает его с SHA этого checkout. На первой попытке устаревший коммит
пропускается; при ручном Re-run старый коммит разрешён.

Сам образ всегда берётся из исходного `build`, даже если скрипты в `main` изменились.
Зависимости приложения здесь не устанавливаются, образ не пересобирается.

### SSH и переменные

`prepare-deploy.sh` запускает `prepare-config.mjs`: проверяются переменные,
создаются файлы подключения и `runtime.conf`. Затем сверяется отпечаток SSH-сервера,
ключ загружается в SSH-агент и проверяется доступ к Docker на VPS.

```text
ВМ deploy
├── WORKSPACE/
│   └── deploy/                      ← скрипты из текущего main
│       ├── deploy.sh, run-deploy.sh
│       └── ci/...
└── RUNNER_TEMP/demetrio-deploy/
    ├── key                          ← приватный ключ из Secrets
    ├── expected-fingerprint         ← ожидаемый отпечаток VPS
    ├── known_hosts                  ← публичный ключ сервера
    ├── ssh_config                   ← настройки подключения
    ├── askpass                      ← помощник для пароля ключа
    ├── agent.sock                   ← сокет SSH-агента
    └── runtime.conf                 ← переменные приложения
```

Папка доступна только владельцу (`700`), секретные файлы — только владельцу (`600`).
На ВМ GitHub это пользователь `runner`. Приватный ключ на VPS не передаётся.

### Получение архива

`download-artifact` скачивает artifact по имени из этой же сборки workflow.
Его идентификатор приходит через `needs.build.outputs.release_id`:

```text
RUNNER_TEMP/demetrio-deploy/
├── key, expected-fingerprint, known_hosts, ssh_config, askpass, agent.sock
├── runtime.conf
└── image.tar.gz                      ← добавлен из artifact GitHub
```

## 4. Передача на VPS — с ВМ GitHub по SSH

`upload-release.sh` создаёт отдельный каталог попытки на VPS и через `scp` копирует
ровно четыре файла. Номер `N` берётся из `GITHUB_RUN_ATTEMPT`. При Re-run образ
остаётся прежним, а каталог меняется: `attempt-1`, `attempt-2` и так далее.
Файлы работающей попытки не перезаписываются; передача в уже существующий каталог
попытки завершается ошибкой. Исходные файлы пока остаются на ВМ GitHub.

Если передача прервана, скрипт пытается удалить архив и конфигурацию только
созданной им попытки на VPS. Если уже появился `runner.lock`, файлы оставляются процессу деплоя:
он удалит их при завершении. При недоступном VPS или принудительном завершении
runner очистка может не выполниться; такие незавершённые передачи нужно удалить
позже, проверив, что их деплой не работает.

```text
ВМ GitHub                                VPS

RUNNER_TEMP/demetrio-deploy/              /opt/demetrio/releases/<release_id>/attempt-<N>/
├── image.tar.gz ──────────────────────► ├── image.tar.gz
└── runtime.conf ──────────────────────► ├── runtime.conf
                                        │
WORKSPACE/deploy/                        │
├── deploy.sh ─────────────────────────► ├── deploy.sh
└── run-deploy.sh ──────────────────────► └── run-deploy.sh
```

Затем по SSH выполняется команда:

```bash
bash /opt/demetrio/releases/<release_id>/attempt-<N>/run-deploy.sh <release_id>
```

`run-deploy.sh` запускает `deploy.sh` в отдельной сессии через `nohup` и `setsid`.
Оба работают на VPS под пользователем `USERNAME` (в текущей настройке — `root`).
ВМ GitHub читает `deploy.log` и получает код завершения из `deploy.exit`.
При обрыве SSH или отмене workflow процесс на VPS продолжает работу до результата.
Репозиторий целиком на VPS не копируется.

## 5. Запуск приложения — VPS

`deploy.sh` выполняет следующие действия:

1. Получает блокировку `deploy.lock` и проверяет файлы рядом со скриптом и существующий контейнер.
2. Очищает старые образы приложения, затем загружает новый через `docker image load`.
3. Проверяет наличие активного `HEALTHCHECK` до остановки старого контейнера.
4. Останавливает старый контейнер и переименовывает его в `demetrio-previous-<release_id>`.
5. Запускает новый `demetrio` из нового образа с переменными из `runtime.conf`.
6. Ждёт состояния `healthy`. При успехе удаляет старый контейнер и повторяет очистку образов.

```text
VPS
├── /opt/demetrio/
│   ├── deploy.lock
│   └── releases/<release_id>/attempt-<N>/
│       ├── deploy.sh, run-deploy.sh
│       ├── deploy.log, deploy.exit, runner.lock
│       ├── image.tar.gz ─── docker image load ──┐
│       └── runtime.conf ─── переменные ──────┐ │
│                                           │ │
└── Docker (логическая схема хранилища)      │ │
    ├── Образ demetrio:<release_id> ◄────────┼─┘
    │       │ запуск                        │
    └── Контейнер demetrio ◄─────────────────┘
        ├── Настройки: переменные, порты, политика перезапуска
        └── Файловая система
            └── /app/
                ├── server.js
                ├── package.json
                ├── node_modules/
                ├── public/
                └── .next/...
```

Хранилище Docker и `/app` контейнера показаны условно: это не подпапки
`/opt/demetrio`. Папка выпуска не монтируется в контейнер.

```text
Браузер → порт 80 на VPS → порт 3000 контейнера → сервер Next
```

Контейнер работает с политикой `unless-stopped`: Docker поднимает его после
перезагрузки VPS, если он не был остановлен вручную. Адрес сайта задаётся в `APP_ORIGIN`.

`HEALTHCHECK` обращается к `/api/health` внутри контейнера. Этот маршрут проверяет
работу Next и корректность конфигурации, но не доступность backend.
При замене контейнеров есть короткий перерыв в доступности сайта.

### Если запуск не удался

До остановки старого контейнера ошибка прерывает деплой, сохраняя его работу.
Если ошибка произошла при замене, скрипт пытается удалить новый контейнер,
вернуть имя старому и запустить его: до пяти попыток с паузой 2 секунды.

При первом деплое предыдущего контейнера нет, поэтому восстанавливать нечего.
Результат восстановления виден в Actions; неудачный деплой остаётся ошибкой джобы.

## 6. Что остаётся после деплоя

На VPS при завершении `deploy.sh`, в том числе при обработанной ошибке, удаляются
`image.tar.gz` и `runtime.conf`. При успешном обновлении получается такая структура:

```text
VPS
├── /opt/demetrio/
│   ├── deploy.lock
│   └── releases/
│       ├── <предыдущий release_id>/
│       │   └── ...
│       └── <новый release_id>/
│           ├── attempt-1/
│           │   ├── deploy.sh
│           │   ├── run-deploy.sh
│           │   ├── deploy.log   ← вывод скрипта
│           │   ├── deploy.exit  ← код завершения: 0 означает успех
│           │   └── runner.lock
│           └── attempt-2/...    ← появится при повторе Deploy
└── Docker
    ├── Работающий контейнер demetrio
    ├── Текущий образ
    └── Сохранённые предыдущие образы
```

Архив больше не нужен: образ уже загружен в Docker. Переменные сохранены в настройках
контейнера, поэтому удаление `runtime.conf` не мешает его работе и перезапуску.
Файлы `deploy.lock` и `runner.lock` остаются, но блокировки снимаются при завершении
процессов. `deploy.log` и `deploy.exit` позволяют проверить результат, даже если
запуск в Actions был отменён. Они появляются по ходу выполнения деплоя.

Очистка образов сохраняет используемые любыми контейнерами образы, предыдущий выпуск
и два свежих неиспользуемых выпуска. Удаляются только старые теги выпусков `demetrio`;
другие приложения не затрагиваются. Папки выпусков со скриптами и логами остаются.
Место на VPS можно проверить командой `docker system df`.

На ВМ GitHub шаг `cleanup.sh` с `if: always()` очищает ключи из SSH-агента и удаляет
всю временную папку `demetrio-deploy`. Затем GitHub удаляет ВМ джобы.
Artifact с образом хранится в GitHub 7 дней; приложение продолжает работать на VPS.

## Проверка и повторный запуск

После первого пуша проверьте обе джобы во вкладке **Actions**, затем откройте сайт
и `/questions`. На VPS можно проверить состояние:

```bash
docker ps --filter name=demetrio
docker inspect --format '{{.State.Health.Status}}' demetrio
```

Для полной цепочки: **Actions → Проверки, сборка и деплой → Run workflow**, ветка `main`.

- Если упал `build`, повторите неудачные джобы: установка, проверки и сборка выполнятся снова.
- Если упал только `deploy`, **Re-run failed jobs** повторит его с готовым artifact.
- Чтобы вернуть прежний коммит, откройте его успешный запуск и повторите только джобу
  **Деплой на VPS**. Используется исходный образ; новый push для отката не нужен.
- При повторе Deploy идентификатор берётся из исходного `build`, а не вычисляется
  заново по номеру попытки Deploy.

Ручной повтор допускает старый коммит и использует текущие Secrets и скрипты `main`.
Убедитесь, что выбрали нужный запуск. Artifact хранится 7 дней; если он недоступен,
**Re-run all jobs** пересоберёт исходный коммит, заново выполнит проверки и деплой.
GitHub разрешает повторы в течение 30 дней после первоначального запуска.
Более старую версию можно вернуть отдельным revert-коммитом в `main`.

Автоматического поиска старого образа на VPS и хранения прошлой конфигурации пока нет.
Пошаговые кейсы — в [deployment-cases.md](deployment-cases.md).

Для перехода на домен настройте HTTPS через обратный прокси, измените публикацию
контейнера на локальный порт и обновите `APP_ORIGIN` перед следующим деплоем.
