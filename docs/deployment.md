# Docker и деплой на VPS

[К основной документации](../README.md)

Файлы деплоя находятся в `deploy/`: `Dockerfile`, его файл исключений
`Dockerfile.dockerignore` и скрипт `deploy.sh`, выполняемый на VPS.
В `deploy/ci/` — скрипты сборки, настройки SSH, передачи выпуска и очистки;
они запускаются из корня репозитория на runner GitHub.
Workflow — в `.github/workflows/production.yml`, где его обнаруживает GitHub Actions.
Контекст Docker-сборки — корень проекта; локальные настройки и секреты исключены.

## Подготовка

На VPS нужны Docker, Bash, `flock`, свободный порт 80 и вход по SSH на порту 22.
Docker Compose не требуется. Публичный ключ должен разрешать вход пользователю деплоя.

В GitHub откройте **Settings → Secrets and variables → Actions → Repository secrets**:

| Secret                 | Значение                                                 |
| ---------------------- | -------------------------------------------------------- |
| `HOST_IP`              | IP вашего VPS без протокола и порта                      |
| `USERNAME`             | `root`                                                   |
| `SSH_PRIVATE_KEY`      | Полный приватный ключ, включая первую и последнюю строки |
| `SSH_HOST_FINGERPRINT` | Только `SHA256:…` — отпечаток ключа VPS                  |
| `API_BASE_URL`         | HTTPS-адрес сервера API без пути                         |
| `APP_ORIGIN`           | Публичный HTTP(S)-адрес приложения без пути              |

Если ключ защищён паролем, добавьте `SSH_KEY_PASSPHRASE`.
При необходимости добавьте `API_UPSTREAM_AUTHORIZATION` и `API_SESSION_COOKIE_NAME`.

Отпечаток получите в доверенной консоли VPS:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Откройте входящий TCP-порт 80 в настройках VPS и firewall, если он включён.
HTTP по IP — временный режим: для авторизации с Secure-cookie нужен HTTPS.

## Автоматический деплой

После пуша в `main` workflow **Деплой на VPS** последовательно выполняет три jobs:

1. `checks` — `npm ci`, ESLint, Prettier, генерация типов маршрутов Next и проверка
   TypeScript. Кеш npm ускоряет скачивание пакетов.
2. `build-image` — установка пакетов и сборка Next внутри Docker;
   готовый образ для `linux/amd64` сохраняется как artifact на 7 дней.
3. `deploy` — скачивание готового образа, проверка SSH и переменных, деплой на VPS.

Если job завершилась ошибкой, следующая не запускается. SSH-ключ и переменные
доступны только в `deploy`; artifact содержит только образ приложения.
Образ передаётся по SSH; переменные внедряются при запуске и не входят в образ.

Контейнер `demetrio` публикует порт `80 → 3000` и перезапускается после перезагрузки VPS.
Сайт доступен по адресу, указанному в `APP_ORIGIN`.
`/api/health` проверяет Next и конфигурацию, без обращения к backend.
Наличие Healthcheck проверяется в образе до остановки старого контейнера.
При неудачном запуске новый контейнер удаляется, затем скрипт делает до пяти
попыток запуска предыдущего с паузой 2 секунды. Результат восстановления виден в Actions.
При замене есть короткий перерыв; это не деплой без простоя.

Скрипты выпусков находятся в `/opt/demetrio/releases/`. Архив образа и файл переменных
удаляются после попытки деплоя. Перед загрузкой образа и после успешного обновления
скрипт очищает старые образы `demetrio`: сохраняет используемые контейнерами,
предыдущий выпуск и два свежих неиспользуемых выпуска. Остальные приложения
не затрагиваются. Свободное место периодически проверяйте через `docker system df`:
переданный архив и сохранённые образы тоже занимают диск.

## Проверка

После первого пуша проверьте workflow во вкладке **Actions**, затем откройте сайт
и `/questions`. На VPS можно проверить состояние:

```bash
docker ps --filter name=demetrio
docker inspect --format '{{.State.Health.Status}}' demetrio
```

Повторный запуск доступен через **Actions → Деплой на VPS → Run workflow** с веткой `main`.
Для упавшего деплоя можно выбрать **Re-run failed jobs**: используется образ
успешной сборки. Если artifact уже удалён, запустите workflow целиком.
Для перехода на домен настройте HTTPS через обратный прокси, измените публикацию
контейнера на локальный порт и обновите `APP_ORIGIN` перед следующим деплоем.
