# Переменные окружения

[К основной документации](../README.md)

Здесь собраны переменные приложения, проверок, Docker и GitHub Actions.
Обычные локальные переменные функций и Bash-скриптов не являются настройками проекта.
Реальные значения секретов в документации не хранятся.

## Где задавать значения

| Где запускается код               | Источник переменных                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------- |
| Локально, `npm run dev`           | Файл `.env.development.local` в корне проекта. `.env.development` тоже поддерживается |
| GitHub Actions, подготовка деплоя | **Settings → Secrets and variables → Actions → Repository secrets**                   |
| Приложение на VPS                 | Деплой формирует `runtime.conf` из Secrets и передаёт его в `docker run --env-file`   |
| Сборка и запуск Docker            | Служебные значения заданы в `deploy/Dockerfile`                                       |

Файлы `.env*` не должны попадать в Git и исключены из Docker-сборки.
Next читает их из корня проекта, а не из `src/`. Уже заданные переменные процесса
имеют приоритет над значениями из файлов. `.env.development` относится к разработке
и не используется при production-запуске.

После изменения локального файла перезапустите dev-сервер. После изменения Secrets
нужен новый деплой: работающий контейнер не получает новые значения автоматически.
Один перезапуск прежнего контейнера его конфигурацию не обновляет.

## Серверные переменные и NEXT*PUBLIC*\*

Сервер Next видит окружение процесса или контейнера. Браузер пользователя
к этому окружению доступа не имеет.

| Вид переменной                   | Где доступна                                      | Когда получает значение                                                                        | Когда использовать                                                           |
| -------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Обычная, например `API_BASE_URL` | В серверном коде через `process.env.API_BASE_URL` | При выполнении серверного кода; если код выполняется при сборке, используется окружение сборки | Для секретов и серверных настроек, которые должны меняться между окружениями |
| С префиксом `NEXT_PUBLIC_`       | В том числе в браузерном коде                     | Next встраивает значение в клиентский JavaScript во время `next build`                         | Для публичных настроек, изменение которых может требовать пересборки         |

Например, прямое обращение `process.env.NEXT_PUBLIC_ANALYTICS_ID` при сборке
заменяется его значением. Новое значение в `runtime.conf` не изменит уже собранный
браузерный код: потребуется новая сборка. Обращение по динамическому имени
`process.env[name]` в браузере такую подстановку не поддерживает.

Чтобы обычная переменная могла меняться без пересборки образа, читайте её на сервере
во время обработки запроса. Если прочитать её при предварительной генерации страницы,
результат может сохраниться в сборке. Для чтения во время запроса можно использовать
`await connection()` из `next/server` в подходящем серверном компоненте.

Если значение нужно браузеру, выберите способ передачи:

| Способ                                                                              | Когда подходит                                                                                                          |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_*`                                                                     | Значение известно при сборке, а пересборка при его изменении устраивает                                                 |
| Сервер читает обычную переменную и передаёт значение или готовую ссылку через props | Настройка нужна компоненту и должна задаваться при запуске контейнера                                                   |
| Отдельный API-маршрут публичной конфигурации                                        | Клиенту удобно получать настройки отдельным запросом; настройки нужно читать при запросе и учитывать кеширование ответа |

Всё, что передано браузеру через JavaScript, props или API, доступно пользователю.
Секреты так передавать нельзя, независимо от префикса переменной.

## Как добавить новую переменную

### Серверная настройка

Например, нужен `LINKS_ORIGIN` — домен для внешних ссылок. Это пример новой настройки,
сейчас такой переменной в проекте нет.

1. Локально добавьте `LINKS_ORIGIN` в `.env.development.local` в корне и перезапустите
   dev-сервер. Значением должен быть нужный адрес с протоколом.
2. В серверном модуле конфигурации читайте `process.env.LINKS_ORIGIN`. Проверьте
   обязательность и формат значения; при необходимости задайте значение по умолчанию.
   Чтение при обработке запроса позволит менять домен без пересборки образа.
3. Для деплоя добавьте Repository secret `LINKS_ORIGIN` в GitHub.
4. В [pipeline.yml](../.github/workflows/pipeline.yml) добавьте его в `env` шага
   **Подготовка SSH и конфигурации**:

   ```yaml
   LINKS_ORIGIN: ${{ secrets.LINKS_ORIGIN }}
   ```

5. В [prepare-config.mjs](../deploy/ci/prepare-config.mjs) добавьте переменную в объект
   `runtime`, чтобы она попала в `runtime.conf`. Если адрес должен иметь те же ограничения,
   что и `APP_ORIGIN`, можно использовать существующий помощник:

   ```js
   LINKS_ORIGIN: getOrigin('LINKS_ORIGIN', true),
   ```

   Этот вариант разрешает HTTPS, а HTTP — только для IP. Для другого формата задайте
   соответствующую проверку. Обязательную настройку также добавьте в массив `required`;
   необязательную — записывайте условно или с согласованным значением по умолчанию.

6. Дополните этот справочник и выполните деплой. Скрипт сам создаст `runtime.conf`,
   передаст его на VPS и задаст значение новому контейнеру.

Добавления одного Secret недостаточно: workflow передаёт только перечисленные в `env`
значения, а `prepare-config.mjs` записывает только явно добавленные в `runtime`.
Вручную редактировать временный `runtime.conf` не нужно.

Для домена ссылок обычно достаточно серверной переменной: сервер формирует ссылку
или передаёт адрес клиентскому компоненту. Если адрес нужен только на сервере,
передавать его клиенту не требуется.

### Публичная настройка при сборке

Например, `NEXT_PUBLIC_ANALYTICS_ID` нужен непосредственно браузерному коду.
Такой переменной сейчас тоже нет в проекте.

1. Локально задайте её в `.env.development.local`, перезапустите dev-сервер
   и используйте прямое обращение `process.env.NEXT_PUBLIC_ANALYTICS_ID`.
2. В GitHub задайте публичное значение в Repository variables или Secrets.
   Само хранение в Secrets не сделает значение приватным после включения в клиентский код.
3. Передайте значение в `env` шага сборки в джобе `build` файла [pipeline.yml](../.github/workflows/pipeline.yml). Для Repository variables
   используется `${{ vars.NEXT_PUBLIC_ANALYTICS_ID }}`, для Secrets — `${{ secrets.NEXT_PUBLIC_ANALYTICS_ID }}`.
4. В [build-image.sh](../deploy/ci/build-image.sh) передайте его в Docker через
   `--build-arg NEXT_PUBLIC_ANALYTICS_ID="$NEXT_PUBLIC_ANALYTICS_ID"`.
5. В [Dockerfile](../deploy/Dockerfile) объявите `ARG NEXT_PUBLIC_ANALYTICS_ID` на стадии
   `builder` до `RUN npm run build`: значение будет доступно Next при сборке.
6. Выполните новую сборку и деплой. Добавлять эту переменную только в `runtime.conf`
   недостаточно.

Текущий CI не передаёт настройки приложения в Docker-сборку; перечисленные
изменения потребуются при появлении первой такой публичной переменной.
Секреты нельзя передавать через публичные переменные или Docker build arguments.

### Другие способы задания

| Способ                                        | Для чего применять                                                                                     |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Окружение команды: `ИМЯ=значение npm run dev` | Разовая локальная проверка без изменения файла                                                         |
| `docker run -e ИМЯ=значение`                  | Передача отдельных настроек при создании контейнера                                                    |
| `docker run --env-file runtime.conf`          | Передача набора настроек при создании контейнера; используется нашим деплоем                           |
| `ENV` в Dockerfile                            | Общие значения по умолчанию, например порт; они сохраняются в образе, поэтому не подходят для секретов |

## Приложение

Эти переменные читаются на сервере в [config.ts](../src/shared/api/server/config.ts).
При деплое имена Secrets совпадают с именами переменных приложения.

| Переменная                   | Назначение                                                                             | Обязательность и значение по умолчанию                                                                                                                                                                  | Секретность                                                                            |
| ---------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `API_BASE_URL`               | Адрес backend. Запросы идут на этот адрес с добавлением `/bxapi/v1/*`                  | Обязательна для работы API и успешного healthcheck. Только HTTPS-адрес без пути, логина, пароля, query и hash                                                                                           | Адрес не является паролем; в текущем workflow хранится в Secrets                       |
| `APP_ORIGIN`                 | Внешний адрес приложения. По нему прокси проверяет `Origin` запросов POST              | Обязательна в production и при деплое. Локально без неё используется origin входящего запроса. Без пути, логина, пароля, query и hash; в production HTTP разрешён только для IP, для домена нужен HTTPS | Публичный адрес, но в текущем workflow хранится в Secrets                              |
| `API_UPSTREAM_AUTHORIZATION` | Полное значение заголовка `Authorization`, который сервер добавляет к запросам backend | Необязательна, по умолчанию заголовок не добавляется. Значение должно соответствовать схеме авторизации backend, включая префикс вроде `Basic`, если он нужен                                           | Секрет. Служебная авторизация перед backend, а не авторизация конкретного пользователя |
| `API_SESSION_COOKIE_NAME`    | Имя сессионной cookie, которую сервер передаёт backend                                 | Необязательна, по умолчанию `PHPSESSID`. Cookies с префиксом `BITRIX_SM_` также передаются                                                                                                              | Имя не является секретом; это не значение cookie и не токен пользователя               |

Внешний адрес `APP_ORIGIN` может отличаться от `API_BASE_URL`: браузер обращается
к своему приложению, а Next передаёт запросы backend. В `APP_ORIGIN` нужно указывать
адрес, который открывает пользователь, а не внутренний адрес контейнера.

В проекте нет переменных `NEXT_PUBLIC_*`. Перечисленные настройки API не встраиваются
в клиентский JavaScript. Авторизация пользователя хранится в сессионных cookies,
а не в переменных окружения.

## Доступ к VPS: GitHub Secrets

Эти Secrets нужны только на ВМ GitHub для подключения к VPS. В образ и в окружение
приложения они не передаются. Workflow переименовывает их для скриптов подготовки:

| Secret в GitHub        | Переменная скрипта     | Назначение и формат                                                                                                                      | Обязательность                                                    | Секретность                                                     |
| ---------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------- |
| `HOST_IP`              | `VPS_HOST`             | IP VPS без протокола, пути и порта; поддерживается IPv4 и IPv6                                                                           | Обязателен                                                        | Адрес не является паролем                                       |
| `USERNAME`             | `VPS_USER`             | Пользователь SSH, в текущей настройке `root`. Под ним выполняется `deploy.sh`, нужен доступ к Docker и `/opt/demetrio`                   | Обязателен                                                        | Имя не является паролем                                         |
| `SSH_PRIVATE_KEY`      | `VPS_PRIVATE_KEY`      | Приватный ключ целиком, с настоящими переносами строк и строками `BEGIN` / `END`. Его публичная часть должна разрешать вход на VPS       | Обязателен                                                        | Секрет. Остаётся на ВМ GitHub, на VPS не копируется             |
| `SSH_HOST_FINGERPRINT` | `VPS_HOST_FINGERPRINT` | Ожидаемый отпечаток ключа SSH-сервера: только `SHA256:…`, без размера ключа и комментария. Проверяет, что подключаемся к нужному серверу | Обязателен                                                        | Не секрет, но значение нужно получать из доверенной консоли VPS |
| `SSH_KEY_PASSPHRASE`   | `VPS_KEY_PASSPHRASE`   | Пароль, заданный при создании приватного ключа                                                                                           | Только если ключ защищён паролем; иначе Secret можно не создавать | Секрет                                                          |

`SSH_HOST_FINGERPRINT` относится к ключу сервера, а не к вашему ключу для входа.
Команда получения отпечатка и подготовка VPS описаны в [документации деплоя](deployment.md#подготовка).

## Docker и локальные проверки

| Переменная                | Кто задаёт                                                              | Назначение                                                                                                                                                                |
| ------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NODE_ENV`                | Next при обычном запуске; в финальном Docker-образе задано `production` | Режим выполнения. Серверная конфигурация использует его для обязательности `APP_ORIGIN` и ограничений HTTP. Вручную для `npm run dev` задавать не требуется               |
| `NEXT_TELEMETRY_DISABLED` | Dockerfile: `1`                                                         | Отключает телеметрию Next при сборке и в контейнере                                                                                                                       |
| `HOSTNAME`                | Dockerfile: `0.0.0.0`                                                   | Интерфейс, на котором сервер внутри контейнера принимает подключения. Это не домен сайта и не `APP_ORIGIN`                                                                |
| `PORT`                    | Dockerfile: `3000`                                                      | Порт Next внутри контейнера. Внешний порт `80` задаётся отдельно через `--publish 80:3000`. Healthcheck тоже использует внутренний порт 3000                              |
| `LINT_TYPE`               | Команды `npm run lint` и `npm run lint:fix`: `code`                     | Выбирает режим ESLint. Сейчас конфиг проверяет наличие значения: без него добавляется IDE-правило проверки неиспользуемых аргументов, с ним используются основные правила |

Эти значения не являются секретами. `PORT` связан с настройками публикации порта
и healthcheck: при его изменении нужно согласованно обновить их.

## Автоматические значения GitHub Actions

Создавать эти переменные в Secrets не нужно: GitHub задаёт их сам.

| Переменная            | Что содержит и где используется                                                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GITHUB_SHA`          | SHA коммита запуска, первая часть тега образа. При Re-run сохраняется исходный SHA. Deploy сравнивает его с checkout текущего `main`                               |
| `GITHUB_RUN_ID`       | ID запуска workflow, вторая часть идентификатора выпуска. При Re-run сохраняется                                                                                   |
| `GITHUB_RUN_ATTEMPT`  | Номер попытки workflow, третья часть идентификатора при сборке. Также задаёт каталог Deploy `attempt-N`; значение больше 1 разрешает ручной деплой старого коммита |
| `GITHUB_OUTPUT`       | Путь к outputs шага: скрипты дописывают туда `release_id=...` или `deploy=true/false`                                                                              |
| `GITHUB_STEP_SUMMARY` | Путь к Markdown-итогам шага: SHA, релиз или причина пропуска                                                                                                       |
| `RUNNER_TEMP`         | Временная папка ВМ: `demetrio-image/` для архива и `demetrio-deploy/` для SSH, конфигурации и скачанного образа                                                    |

Встроенный `GITHUB_TOKEN` используется Actions автоматически; свой Secret создавать
не нужно. Workflow имеет только `contents: read`. Скрипты не обращаются к GitHub API
и не получают токен через `env`. SSH-ключ и настройки приложения передаются только
шагу подготовки деплоя.

В YAML используются контексты GitHub, а не переменные окружения Bash:

| Значение                         | Назначение                                                                                              |
| -------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `github.ref`                     | Ветка запуска и часть группы отмены проверок. Только `refs/heads/main` допускает сборку образа и Deploy |
| `runner.temp`                    | Путь временной папки; соответствует `RUNNER_TEMP`                                                       |
| `secrets.<имя>`                  | Чтение Secret для передачи в `env` шага подготовки                                                      |
| `steps.image.outputs.release_id` | Output шага сборки: имя artifact и output джобы `build`                                                 |
| `needs.build.outputs.release_id` | Исходный выпуск в Deploy: проверка, имя скачиваемого artifact и аргумент передачи на VPS                |
| `needs.build.result`             | Результат джобы проверок и сборки: Deploy допускается только в `main` после `success`                   |
| `steps.release.outputs.deploy`   | `true` разрешает SSH и обновление, `false` пропускает устаревший автоматический релиз                   |

## Значения, которые создают скрипты

Их не нужно добавлять в Secrets или локальный файл окружения.

| Переменная            | Кто задаёт и зачем                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RELEASE_ID`          | Workflow из `needs.build.outputs.release_id`: передаёт готовый выпуск в `check-release.sh` и `upload-release.sh`, затем аргументом в скрипты VPS                    |
| `SSH_AUTH_SOCK`       | `prepare-deploy.sh` и `cleanup.sh` для `ssh-add`: сокет `RUNNER_TEMP/demetrio-deploy/agent.sock`. SSH/SCP получают тот же путь через `IdentityAgent` в `ssh_config` |
| `SSH_ASKPASS`         | `prepare-deploy.sh`: путь к помощнику `askpass`, который возвращает пароль из `VPS_KEY_PASSPHRASE`                                                                  |
| `SSH_ASKPASS_REQUIRE` | `prepare-deploy.sh`: `force`, чтобы `ssh-add` использовал `askpass` без интерактивного ввода                                                                        |
| `DISPLAY`             | `prepare-deploy.sh`: `:0`, служебное значение для `askpass`; графический интерфейс не запускается                                                                   |

`release_id` в outputs и локальная переменная `release_id` обозначают тот же выпуск,
что и `RELEASE_ID`: `<SHA>-<ID запуска>-<номер попытки сборки>`. Он определяет тег
образа, имя artifact и каталог `/opt/demetrio/releases/<release_id>/`.
При повторе только Deploy используется прежний output `build`, поэтому идентификатор
не меняется вслед за номером попытки Deploy. Внутри каталога выпуска файлы каждого
Deploy лежат отдельно: `attempt-N`, где `N` — текущий `GITHUB_RUN_ATTEMPT`.
Тег образа от этого номера повторного Deploy не меняется.

## Как настройки доходят до приложения

```text
Разработка:
Файл .env.development.local в корне → Next → серверная конфигурация API

Деплой:
Repository secrets
  ├── SSH-настройки → временные файлы на ВМ GitHub → подключение к VPS
  └── Настройки приложения → runtime.conf → передача на VPS
                                            │
                                            ▼
                              docker run --env-file runtime.conf
                                            │
                                            ▼
                                 Окружение нового контейнера
```

После попытки деплоя `runtime.conf` удаляется. Docker уже сохранил переменные
в настройках контейнера. Их могут прочитать администраторы с доступом к Docker;
не публикуйте вывод инспекции окружения контейнера и содержимое файлов с секретами.
